## 一、需求背景与目的

1. 目前量化王在外部渠道做账号运营，涉及平台包括：**小红书、抖音、百度、微博、视频号**，后续准备通过这些渠道进行引流，引导用户下载量化王APP
2. 需要针对每个渠道来源进行区分，统计各渠道的引流效果数据（扫码量、点击下载量），为运营决策提供数据支撑
3. 目前已有现成的中间下载页（`https://yd-zbj.yd.com.cn/appDownload`），本次需求在此基础上增加渠道标识与数据统计能力

## 二、需求清单

| 功能模块 | 详细说明 |
|---------|---------|
| 渠道二维码生成 | 为每个外部渠道生成带有渠道标识参数的专属二维码，共5个渠道 |
| 中间下载页增加渠道统计 | 现有下载页增加渠道参数识别能力，页面加载时读取 `channel` 参数并记录，点击下载时上报渠道数据 |
| 后台数据看板 | 在管理后台"APP用户数据"分类下新增渠道统计图表，展示各渠道的扫码量、下载量与转化漏斗 |
| 数据表设计 | 新增事件明细表（`t_channel_event_log`）和日汇总统计表（`t_channel_daily_stats`） |

## 三、需求详情

### 3.1 渠道二维码

#### 渠道列表

每个渠道对应一个专属下载链接，链接通过 `channel` 参数区分渠道来源：

| 渠道 | channel 参数值 | 完整链接 |
|------|---------------|---------|
| 小红书 | xiaohongshu | `https://yd-zbj.yd.com.cn/appDownload?channel=xiaohongshu` |
| 抖音 | douyin | `https://yd-zbj.yd.com.cn/appDownload?channel=douyin` |
| 百度 | baidu | `https://yd-zbj.yd.com.cn/appDownload?channel=baidu` |
| 微博 | weibo | `https://yd-zbj.yd.com.cn/appDownload?channel=weibo` |
| 视频号 | shipinhao | `https://yd-zbj.yd.com.cn/appDownload?channel=shipinhao` |

#### 二维码生成规则

1. 每个渠道的二维码内容为上表中的完整链接
2. 二维码样式统一，配合量化王品牌视觉（参考现有下载引导图样式：左侧二维码 + 右侧文案"长按图片识别二维码 或在应用市场搜索'量化王'下载"）
3. 后续如新增渠道，按相同规则新增 `channel` 参数值即可

#### 各平台投放说明

| 渠道 | 投放方式 | 注意事项 |
|------|---------|---------|
| 小红书 | 笔记中以图片形式嵌入二维码 | 小红书对外链管控较严，不建议直接放链接，以图片形式展示二维码，用户截图后扫码 |
| 抖音 | 视频/主页中以图片形式展示二维码 | 抖音内置浏览器会拦截直接跳转商店，中间下载页需引导用户"在浏览器中打开" |
| 百度 | 百家号文章/搜索推广中放置链接或二维码 | 百度环境对外链相对友好，302跳转基本正常 |
| 微博 | 微博正文/评论中以图片形式展示二维码 | 微博内置浏览器有一定拦截，中间下载页需引导用户"在浏览器中打开" |
| 视频号 | 视频号动态/直播中以图片形式展示二维码 | 微信内置浏览器对外链管控最严格，中间下载页必须引导用户"在浏览器中打开"后才能正常跳转商店 |

### 3.2 现有中间下载页增加渠道统计

#### 现有页面（无需新建页面）

- 页面地址：`https://yd-zbj.yd.com.cn/appDownload`
- 现有功能：展示下载引导信息，用户点击下载按钮后根据手机系统（iOS/Android）跳转到对应应用商店
- **本次不新建页面**，所有渠道二维码扫码后统一跳转到此现有页面，仅在现有页面基础上增加渠道参数识别与数据上报逻辑

#### 需要增加的逻辑

1. **页面加载时**：读取 URL 中的 `channel` 参数，若存在则存入页面上下文（如 localStorage 或内存变量），同时上报一条"扫码访问"事件
2. **点击下载按钮时**：
   - 上报一条"点击下载"事件，携带 `channel` 参数值和用户设备信息（iOS/Android）
   - 上报完成后，按现有逻辑跳转到对应平台的应用商店（此处逻辑不变）
3. **内置浏览器兼容处理**（如现有页面已有则无需重复开发）：检测当前浏览器环境（微信、抖音、微博等内置浏览器），若为内置浏览器，展示引导蒙层提示用户"点击右上角 → 在浏览器中打开"，以确保后续跳转商店正常
4. **无 channel 参数时**：页面表现与现有逻辑完全一致，不受影响。数据上报时渠道记录为"直接访问"或"未知渠道"

#### 页面UI与交互

无变化，保持现有样式和交互流程不变。

### 3.3 渠道数据统计

#### 统计节点

数据统计分为两个节点，形成转化漏斗：

| 统计节点 | 触发时机 | 记录字段 |
|---------|---------|---------|
| 扫码访问（PV/UV） | 中间下载页加载完成时 | channel、访问时间、设备类型（iOS/Android）、UA、IP |
| 点击下载 | 用户点击下载按钮时 | channel、点击时间、设备类型（iOS/Android）、UA、IP |

#### 核心指标

| 指标 | 说明 |
|------|------|
| 扫码访问量（PV） | 各渠道下载页的页面浏览次数 |
| 扫码访问人数（UV） | 各渠道下载页的独立访客数 |
| 点击下载量 | 各渠道用户点击下载按钮的次数 |
| 点击下载人数 | 各渠道点击下载按钮的独立用户数 |
| 下载转化率 | 点击下载人数 / 扫码访问人数 × 100% |

#### 数据上报字段

| 字段 | 说明 | 示例 |
|------|------|------|
| event_type | 事件类型 | `page_view` / `click_download` |
| channel | 渠道标识 | `xiaohongshu` / `douyin` / `baidu` / `weibo` / `shipinhao` |
| device_type | 设备类型 | `iOS` / `Android` |
| user_agent | 浏览器UA | 用于判断内置浏览器环境 |
| ip | 用户IP | - |
| timestamp | 事件时间戳 | - |

### 3.5 数据表设计

#### 事件明细表：`t_channel_event_log`

记录每一次扫码访问和点击下载的原始事件数据。

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| id | bigint | 是 | 主键，自增 |
| event_type | varchar(32) | 是 | 事件类型：`page_view`（扫码访问）/ `click_download`（点击下载） |
| channel | varchar(32) | 是 | 渠道标识：`xiaohongshu` / `douyin` / `baidu` / `weibo` / `shipinhao` / `unknown` |
| device_type | varchar(16) | 是 | 设备类型：`iOS` / `Android` / `unknown` |
| ip | varchar(64) | 否 | 用户IP地址 |
| user_agent | varchar(512) | 否 | 浏览器UA |
| fingerprint | varchar(128) | 否 | 访客指纹（IP+UA拼接生成hash，用于UV去重） |
| referer | varchar(256) | 否 | 来源页面URL（可辅助判断实际来源） |
| created_at | datetime | 是 | 事件发生时间 |

索引建议：`channel` + `created_at` 联合索引，`event_type` + `created_at` 联合索引

#### 日汇总统计表：`t_channel_daily_stats`

按日按渠道汇总的统计数据，供后台看板直接查询，避免每次从明细表实时聚合。

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| id | bigint | 是 | 主键，自增 |
| stat_date | date | 是 | 统计日期 |
| channel | varchar(32) | 是 | 渠道标识 |
| page_view_pv | int | 是 | 当日扫码访问量(PV) |
| page_view_uv | int | 是 | 当日扫码访问人数(UV) |
| click_download_pv | int | 是 | 当日点击下载量 |
| click_download_uv | int | 是 | 当日点击下载人数 |
| click_download_ios | int | 是 | 当日iOS点击下载量 |
| click_download_android | int | 是 | 当日Android点击下载量 |
| download_convert_rate | decimal(5,2) | 是 | 当日下载转化率(%) |
| created_at | datetime | 是 | 记录创建时间 |
| updated_at | datetime | 是 | 记录更新时间 |

索引建议：`stat_date` + `channel` 联合唯一索引

数据生成方式：通过定时任务每日凌晨从 `t_channel_event_log` 聚合前一天的数据写入此表

## 四、埋点说明

### 中间下载页

页面中涉及的事件有：**页面浏览、点击下载**

可能使用到的属性字段：

1. screen_name = `app_download`
2. title = `APP下载页`
3. tab = `/`
4. element_position = `/`
5. element_id = `/`
6. element_content = `下载按钮` / `引导蒙层`
7. form = `/`
8. element_type = `button`（点击下载）/ `link`（跳转商店）
9. content_id = `/`
10. channel = 渠道标识（`xiaohongshu` / `douyin` / `baidu` / `weibo` / `shipinhao` / 空）
11. device_type = `iOS` / `Android`

## 五、补充说明

1. **关于实际安装归因**：本方案统计的是"扫码访问"和"点击下载"两个节点，无法追踪用户跳转到应用商店后是否真正完成了安装。如后续需要精确到"实际安装激活"级别的归因，可考虑以下方案：
   - Android：为每个渠道打渠道包（在APK中写入渠道标识，安装后App读取上报）
   - iOS/Android 通用：接入第三方归因平台（如 openinstall），通过 Deferred Deep Link 技术实现安装归因
2. **渠道扩展性**：后续如新增运营渠道，只需新增对应的 `channel` 参数值，生成新的二维码即可，中间下载页和统计后台无需改动
3. **二维码管理**：建议在后台提供二维码生成与管理功能，运营人员可自助创建新渠道的二维码，避免每次新增渠道都需要开发介入
